The infrastructure I built

I built the path from the partner’s application to each lender’s decision. Partners submit one data format. Inside Ping3, each lender has its own required fields and request format. I could add the next lender on the platform side.

What if a partner submits an application and the connection drops before the acknowledgement arrives? The partner can resend it with the same ID. Ping3 recognises the retry, acknowledges receipt and keeps a single application for the customer.

Four events in one application

Illustrative example. A customer submits one application. Lender A returns an offer while lender B is still reviewing it. The customer takes offer A, and A later confirms the loan was funded.

  1. PartnerSubmits one application
  2. Ping3Prepares separate requests
  3. LendersReview the applications
  4. PartnerReceives offers and funding status
  1. 01Application accepted

    Ping3 accepts the form through the partner API. Subsequent results can be linked back to the original application.

  2. 02Requests sent

    Ping3 sends the data in the format each eligible lender requires. Each lender assesses the application independently.

  3. 03Offers delivered

    Ping3 sends approved offers back in a batch. Each offer includes the approval type, amount, term, rate and a link to continue. If delivery fails, Ping3 retries.

  4. 04Funding confirmed

    The lender reports funding separately and identifies the offer the customer used. A repeat notification for the same funded loan can be processed without counting it twice.

Offer and funding are separate events

The two events answer different questions. An offer gives the customer a choice. Funding confirmation tells the partner whether the customer received the money. Counting both as one kind of conversion would make a route with more offers look stronger even if funding stayed flat.

How I optimise payment processing

I choose payment providers for each legal entity. Payment success rates vary by entity and provider, so I regularly compare the results for each combination and revisit which provider to use.

For example, when payment success falls, two questions narrow the search. How many attempts did the bank authorise? How many ended in a completed payment? If the approval rate holds steady but fewer payments complete on the same number of attempts, the next place to look is after authorisation.

How I would test the hypothesis

Testing the contribution of a new lender

Metric

I’d assess a new lender on the share of applications with at least one confirmed funded loan in the same observation window. An application with multiple offers counts once.

Test

I’d randomly assign eligible applications to the current pool or to the same pool plus the new lender. A lift in the share with confirmed funding would support expanding the network. If the mix of lenders changes but overall funding stays flat, the decision depends on integration and maintenance costs.

I’d also check time to first offer and the completeness of funding updates. If the new lender reports funding late, part of the difference may only appear with a longer observation window.
